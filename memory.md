## Cycle de vie du moteur — le point sensible

Le moteur est un processus Go qui annonce périodiquement au tracker ; le tuer brutalement laisse une **annonce « stopped » manquante** et peut laisser un **orphelin qui continue d'annoncer**.

| Situation | Mécanisme |
|---|---|
| Arrêt demandé (`stop_session`) | `CTRL_BREAK_EVENT` sous Windows (l'appelant fait `AttachConsole(pid)` au préalable, sinon l'appel système renvoie succès sans rien délivrer), `SIGTERM` au groupe sur Unix. Go le traduit en `os.Interrupt` → annonce finale « stopped ». |
| Moteur qui ne répond pas | Tué de force après 10 s (`STOP_GRACE_PERIOD`). |
| Fermeture de l'application (`quit_app`, Ctrl+Q) | Arrêt propre de tous les moteurs, délai `SHUTDOWN_GRACE_PERIOD` = 3 s, puis kill. |
| **Crash de l'application** | Chaque moteur est rattaché à un **job Windows `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`** : le handle du job n'est jamais fermé par notre code, c'est Windows qui le libère quand le processus disparaît → tous les moteurs du job sont tués. |
| Job indisponible / rattachement refusé | L'échec est **inscrit en avertissement dans le journal de la session** (`log_orphan_protection`) — jamais silencieux : l'utilisateur voit que la garantie anti-orphelin est perdue, alors que l'arrêt normal reste effectif. |

Détail Windows : `GenerateConsoleCtrlEvent` **renvoie succès même quand rien n'atteint la cible** ; l'événement ne touche qu'un groupe de processus d'une console à laquelle l'appelant est attaché. Ces deux pièges ont été établis par des spikes Go/Rust avant l'écriture du code.

L'utilisateur l'a proposé : l'idée est meilleure que la mienne (je proposais de supprimer la fenêtre entière, ce qui n'aurait laissé que la version — déjà visible dans le bandeau de l'en-tête).
- **`BuildInfo` réduit à `version`.** `commands.rs` n'expose plus `commit` / `commit_date` ; le test `build_info_identifies_the_binary` vérifie que la version n'est jamais vide (une version vide laisserait un trou ; l'ancien test vérifiait commit + date, qui n'existent plus).
- **`src-tauri/build.rs` réduit à `tauri_build::build()`.** Plus aucune requête git au build : ni `rev-parse`, ni `show`, ni `status`, ni `RSM_COMMIT` / `RSM_COMMIT_DATE`. Le fichier est conservé (le script doit appeler `tauri_build::build()`) et documente pourquoi il ne fait plus rien d'autre. La version vient de `CARGO_PKG_VERSION`, lue sans git.
- **Statut de mise à jour mémorisé** (`updateStatus` / `updateStatusError`) : la vérification de démarrage, pourtant silencieuse, renseigne l'état. Ouvrir « A propos » montre donc l'etat reel, pas un « jamais verifie » trompeur. Si la fenêtre est ouverte **pendant** la vérification asynchrone, le statut est repeint après coup (sinon elle resterait vide plusieurs secondes).

## Version 2.0.10 (10/10/2026) — correctif de la 2.0.9 cassée

- **La 2.0.9 affichait une fenêtre vide.** Une seule ligne : `${this.icons.download}` dans le gabarit de la modale « A propos ». `App` n'a **jamais** eu de propriété `icons` — les icônes sont dans la constante `ICONS`, et `this.icons` n'existe que dans `NewSessionForm` (L18) et `SessionCard` (L6), qui reçoivent leurs icônes par `options.icons`. Lire `this.icons.download` sur une instance `App` lève `TypeError: Cannot read properties of undefined (reading 'download')`.
- **Pourquoi toute la fenêtre était vide, et pas seulement le bouton :** le `TypeError` est levé pendant l'**évaluation du littéral de gabarit**, c'est-à-dire *avant* l'affectation `app.innerHTML = \`…\``. L'exception remonte hors de `render()`, `#app` reste vide — pas même l'en-tête. Aucun message, aucune trace : l'app est vivante, sa fenêtre noire. C'est ce qui rend ce genre de faute très discret.
- **Détecté trop tard.** La CI a passé au vert : `node --check` ne voit qu'une erreur de **syntaxe**, or le bundle était syntaxiquement valide. Le test qui aurait dû le voir (`cargo test`, clippy) ne touche pas au JS du frontend, et aucun test frontend n'existe. **Rien dans la chaîne ne vérifie que le frontend s'exécute sans lever.**
- **Correctif :** `${ICONS.download}`. Vérifié par un harnais qui rejoue l'évaluation du gabarit : l'ancien code lève bien le `TypeError` exact, le nouveau s'évalue sans lever (icône de 589 caractères rendue), et `this.icons` a **0 occurrence** dans `app.js`.
- **Piège à retenir :** dans une classe instanciée sans `icons` dans son constructeur, `this.icons.x` échoue silencieusement à l'écran. Utiliser la constante `ICONS` directement dans `App`, qui n'a pas d'icônes injectées. `this.icons` reste **légitime** dans les deux classes qui le définissent — ne pas le « corriger » globalement.

## Limite de mise à jour : `requireSignedVersion` inutilisable ici (10/10/2026)

- **Constat :** `tauri-plugin-updater` 2.13.2 protège contre l'attaque par rétrogradation (un endpoint compromis annonce `version: 999.0` mais sert l'URL + la signature d'une release ancienne, validement signée). Deux options : `requireSignedVersion` et `allow_downgrades`. **Les deux sont à `false` par défaut.**
- **Pourquoi on ne peut pas activer `requireSignedVersion` :** l'option exige que la signature porte la version dans son *trusted comment* (couvert par la signature). Or la signature publiée pour v2.0.6 contient :
  ```
  timestamp:1791626725	file:Ratio Spoof Manager_2.0.6_x64-setup.exe
  ```
  **Pas de champ `version:`** — le CLI Tauri de ce projet n'en écrit pas. Activer le drapeau ferait échouer toute mise à jour avec `Error::MissingSignedVersion`. Il faudrait d'abord réémettre **toutes** les releases atteignables par les utilisateurs avec un CLI écrivant ce champ, ce qui n'est pas acquis ici.
- **Conséquence :** le modèle « installateur signé + `/UPDATE` » reste en place, tel que conçu et testé par Tauri. Une réécriture de la vérification de signature à la main n'apporterait rien : le plugin utilise déjà `minisign_verify` et traite correctement le *trusted comment* (lu **seulement après** `public_key.verify(...)` — le lire avant, ce serait faire confiance à des données contrôlées par l'attaquant).
- **Mise à jour in-place du portable : étudiée puis abandonnée.** Le principe (dossier `versions/<v>/` + pointeur `current.txt` + lanceur) a été écrit et testé — lanceur Rust de 206 Ko, 6 tests verts, relance de code de sortie vérifiée — puis supprimé : Windows interdit d'écraser un `.exe` en cours d'exécution, l'alternative est fragile, et elle n'apporte qu'un dossier de moins dans `AppData` face à un modèle que Tauri répare depuis des années. Le modèle installer est **prouvé en conditions réelles** : la 2.0.6 s'est installée seule.

## Points ouverts / limites connues

- **Aucun équivalent Unix du job** : sur Linux/macOS, un crash de l'application laisse encore les moteurs vivants (seul l'arrêt explicite est couvert).
- **Rétrogradation possible via l'updater** : tant que `requireSignedVersion` reste inutilisable, un endpoint compromis peut faire installer une release ancienne mais signée. Le vecteur suppose le contrôle du serveur GitHub ou du réseau ; le risque est réel mais faible. À revoir si la chaîne de signature évolue.
- **Déploiement hors dépôt :** le binaire de `D:\0day\` est piloté par l'utilisateur, pas par ce dépôt. Ne jamais y copier d'exécutable sans demande explicite — `D:\Codex\ratio-spoof-manager-tauri` est le seul périmètre de travail.
- La **cross-compilation complète** du crate pour Linux n'est pas vérifiable ici (sysroot GTK absent) ; le module Unix isolé a été compilé pour `x86_64-unknown-linux-gnu` via un `rustc` ciblé.
- `cargo clippy --all-targets -- -D warnings` est **propre** (vérifié le 14/09/2026) ; l'ancien avertissement `manual Range::contains` dans `extract_ratio` a disparu avec la réécriture du parsing.
- **Parsing des stats (réécrit le 14/09/2026) :** les parsers collent désormais au **format réel** de `printer.go`, vérifié dans le dépôt moteur — `humanReadableSize` écrit des unités IEC **sans espace** (`800.00MiB`, `1.50GiB`, `2.00KiB/s`) et jamais des « MB »/« kbps ». Les anciens extracteurs (`extract_speed`, `extract_size_mb`, `extract_ratio`…) cherchaient `mb`/`gb`/`mbps` : ils **ne matchaient jamais** la sortie du moteur, et l'interface n'affichait que l'estimation temporelle du fallback. Nouveau découplage : `update_stats_from_log` lit la ligne d'annonce `#N downloaded: X(4.00%) | left: Y | uploaded: Z` (totaux cumulés + progression + ratio, horodatés dans `last_announce`) et le bloc d'en-tête `Download Speed:` / `Upload Speed:` (vitesses courantes) via `parse_size_after`/`parse_percent_after`. Les champs JSON (`total_uploaded_mb`, `current_upload_speed` en kB/s binaires) sont conservés pour ne pas casser le frontend. **Couplage assumé :** tout changement de `humanReadableSize`/du gabarit de printer.go casse ce parsing — les tests `announce_line_feeds_totals_progress_and_ratio` etc. verrouillent le format attendu. En amont, le moteur n'accepte que `kbps`/`mbps` (base 1024, `input.go::validSpeedSufixes`) et `%|b|kb|mb|gb|tb` pour les tailles : `parse_speed_config` renvoie des **octets/seconde** (l'ancienne version multipliait par 1000 et acceptait `gbps`/`bps` que le moteur rejette), la validation du formulaire (`NewSessionForm.js`) est alignée sur celle du backend (`commands.rs::validate_field`, qui avait déjà raison), et les espaces internes de saisie sont retirés avant envoi (`5 mbps` faisait échouer le `ParseFloat` du moteur).
- Fichiers volontairement **non versionnés** : `.cache/` (outils locaux), `dist/` (bundle Vite), `node_modules/`, `src-tauri/target/`, `src-tauri/binaries/*` (sidecar téléchargé).
- **Nettoyage du 13/09/2026 :** ~6,5 Go libérés (`node_modules/`, `src-tauri/target/`, ancien sidecar de 2021, archive de l'historique écrasé, `rsm_ultra.zip`), puis ~400 Ko de sources moteur retirées de ce dépôt (déménagées dans `Endymi0n74/ratio-spoof`). Seul le **Go portable** est conservé dans `.cache/go` (Go n'est pas installé sur la machine) : il sert désormais à construire le dépôt moteur, pas l'interface.
